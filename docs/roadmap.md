# 开发规划

这份规划按当前 `ashare` 仓库执行：Go + PostgreSQL + 现有 Web，主数据源为官方 Tushare。

优先级：

**数据可信度 > 回测可信度 > 风险控制 > 研究质量 > 策略复杂度 > 技术炫技。**

## 原则

- 主链路继续 Go + PostgreSQL + 现有 Web。研究脚本以后用 Python 读库，不推倒重写成 Python 项目。
- 主数据源继续官方 Tushare。AkShare、券商导出只做抽查和补洞。
- AI 只处理公告和研报这类非结构化信息。收益、仓位、撮合、风控一律用确定性代码。
- 每一阶段做完能跑、能看、能复现，再进入下一阶段。不承诺收益。

## 现在已经有的

行情底座已经通：证券、交易日历、未复权日线、复权因子、涨跌停、停牌、限流、幂等入库、K 线质检和页面上同步。这相当于行情存储阶段，语言是 Go。

## 阶段

### 1. 把日线数据钉死

补齐缺日检查、重复灌数不脏数据、单位约定（股/元）、复权与未复权分开。把「ST 只是当前名称、没有历史 ST 快照」这类限制写进文档。

验收：同一区间重跑结果一致；看板能看出缺日；涨跌停和停牌能在图上对上。

### 2. 最小回测

先做一只股票或一个很简单的规则（例如均线或动量），严格按 T 日信号、T+1 成交。计入佣金、印花税、滑点；涨停买不进、跌停卖不出、停牌不成交、现金不够不能买。输出收益、回撤、交易明细，并能用同一份数据重跑。

验收：手工能对上几笔成交；报告里写明还没覆盖的规则（整手、分红现金、退市）。

当前状态：已落地。`ashare backtest`、`POST /api/backtest`、看板「最小回测」页。规则与限制见 [backtest.md](backtest.md)。

### 3. 组合与风控

股票池用当时的指数成分或流动性过滤，不要用今天还在市的股票回测十年。定期再平衡，限制单票仓位、总仓位和最小成交额。

验收：不能无限加仓；调仓记录可追溯。

### 4. 财务数据

只在 Tushare 能提供披露日时才接入。区分报告期和实际可见日。没有历史披露快照的字段，只用于看现在，不进回测。

验收：能举出「这份财报在某日还不能用」的例子。

### 5. 可解释评分

基本面、行业、估值、趋势拆开打分，权重写在配置里并记录版本。评分高不等于买入。

验收：每只股票能指出分数来自哪几项，而不是一个黑箱数字。

### 6. AI 研究

在回测可信之后再做。先做公告摘要和事件抽取，保留来源、时间和证据等级，相同内容缓存，控制调用费用。模型不能下单，也不能把推断写成事实。

### 7. 模拟盘与订单草案

策略产出目标仓位，生成订单草案，在页面上批准后才记入模拟成交。默认没有真实下单。订单要有状态：未批、已批、过期、部分成交、状态不明。

### 8. 券商实盘

只有明确要求，并确认券商、账户权限和接口之后才做。真实交易默认关闭，且与 AI 模块隔离。

## 顺序与预算

顺序是 1 → 2 → 3，然后才是 4 和 5。第 6 步往后不提前做。

费用控制在 Tushare 日线所需积分。先不买分钟线，也不对全市场公告做无差别的大模型分析。

下一步是第 3 步：组合与风控（指数成分或流动性过滤、仓位上限）。第 1 步里还缺的历史 ST 快照不在本阶段补。
